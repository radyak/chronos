# Phase 0 - Idea

The base idea of *"Chronos"* is to establish a model of historical data, but also to provide query and display tools that allow users to investigate, create infographics and share insights.

## Audience and Use Cases
*Chronos* should target - or at least consider - both, advanced/academic as well as standard/unexperienced users in the field of historical sciences:
* **Professional users** could curate and contribute data, profit from advanced query and graphical features.
Later on, the might be able to start or take part in discussions, support other users, provide content to fill data and graphics with life and profit themselve for studies and research.
* **Standard users** could browse data, build simple to advanced queries, create info graphics and thus could be enchanted for the field of history.
In a future stage, they might even be possible to create or use pre-structured and ready-to-use building blocks for querying, data transformation, graphical representation - or even whole info graphics. All these can be shared and reused as base for further usage. Together with discussions and content feeds, *Chronos* could become a sort of Social Network for History.


## Monetization
In its basic usage, the platform should be free to use, and might be crowd-funded or supported by foundations or donations.
Only advanced and especially resource-consuming use cases might require paid subscriptions or licenses.

## Components
They key components are explained below.

### Historical Data & Model
The Historical Data is the backbone of *Chronos*. The **model**, that defines the shape and content of the data, should
* allow to reflect historical data as correctly, flexible and extensible as possible
* considers sources, evidences and debated facts
* be able to reflect blurry facts such as fuzzy dates / date ranges

The model of the Historical Data is defined by a **schema**, which defines. Both, schema and data must be **administrable**, i.e. there should a process or lifecycle of editing, review, correction, approval and release should be supported.

### User Interface
The User Interface should provide basic access to everyone, but user-specific permissions should distinguish which features a user can use.
* **Exploration**: There should be a section where users can browse Historical Data in different formats and graphical representation. Also random suggestions for data, data sets and pre-built info graphics should be available there. Besides browsing, users should also be able to specifically query data - as user-friendly as possible, e.g. using a graphical query builder and/or using query blocks. A similar pattern for building blocks, the queried data could be transformed, so that it can fit and be displayed in different graph types, which can also be configured. In the future, these graphs should be possible to save, publish and share with other users.
* **Administration**: The underlying data and meta data must be administered and curated by trusted, professional users. Depending on the data, the process of maintenance might involve four-eye-principle, versioning and tasks/notification to request respective actions. This involves the following aspects:
  * Schema
  * Data
  * Sources
  * Labels
